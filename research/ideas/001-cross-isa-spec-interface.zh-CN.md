# 用共同规格隔离跨 ISA 顶层验证与完整模型

记录日期：2026-10-02。状态：用户已澄清目标，并质疑总体难度是否降低；应与直接关系验证对照评估。

**核心想法**：为 kernel 建立对每个合法输入唯一确定可观察输出的共同规格。NEON 和 RVV 分别在各自完整模型下证明符合该规格，并导出可组合的证明接口。跨 ISA 的顶层等价证明只使用共同规格、两侧符合性定理及必要前提，从而避免在顶层同时展开和处理两个完整 ISA 模型。

**用户原话**：

> 第一个是，对于一个kernel的语义信息，或者对其的spec，我们可以这样创造，来避免直接两个程序合并在一起证明，以及类型的不对齐：这里我们规定，对于所有的合法输入，都有一个确定的output是一个确定性的，这样是一个完整的语义刻画，如果我们只关心output的话

用户随后明确了主要目的：

> 我这个主要是为了cross isa的验证在顶层验证的时候不必去面对两个完整模型

用户进一步提出收益方面的疑问：

> 那为什么我们不直接联合起来验证？这个难度好像并没有降低多少

**当前整理**：共同规格充当跨 ISA 验证的抽象接口。完整的指令语义、寄存器类型、循环状态和内存表示由各侧证明处理；顶层组合的是关于同一抽象输入和输出的结论。类型差异集中在各侧与共同接口的对应证明中。

共同规格可以是函数 `F : Input → Output`，也可以是关系 `Spec(x, y)`，满足对每个合法输入 `x`，存在唯一的 `y` 使 `Spec(x, y)` 成立。两侧分别证明其可观察输出满足同一个规格，再由唯一性推出输出相等。这里需要具体的共同输入—输出关系；仅知道两份程序各自具有确定性，不能推出等价。

**助手补充的成立条件**：

- 共同输入包含所有影响输出的信息，两边覆盖同一个约定的合法域。例：当前 reduction 的输入包含字节序列和输出地址的初值。
- 两侧分别证明具体输入和输出表示与共同类型的对应关系；顶层无需比较完整机器状态。
- 只证明返回时的输出符合规格，得到的是关于返回结果的结论。若要求每个合法输入都正常返回，还需相应终止性和执行安全义务。
- 完整模型继续作为底层证明的依据；逻辑上无需在顶层展开模型，与工具是否加载模型依赖是两个问题。所有未解除的证明前提仍须显式保留。

**项目中的已有依据**：

- [KernelSpec.v](../sail-tooling-gap/kernel-e2e/KernelSpec.v) 已定义共同的 `byte_reduction_spec`，表达 `(old + sum(input)) mod 2^32`。但该文件仍导入 AArch64 和 NEON 证明模块，尚不能据此认定共同接口已经与完整模型隔离。
- [NeonByteSpec.v](../sail-tooling-gap/kernel-e2e/NeonByteSpec.v) 和 [RvvByteSpecConditional.v](../sail-tooling-gap/kernel-e2e/RvvByteSpecConditional.v) 已包含面向共同规格的两侧定理。RVV 定理仍显式依赖 `Hload`，完整跨 ISA 结论尚未闭合，详见 [检查点](../sail-tooling-gap/CHECKPOINT.md)。

上述判断来自本次源码阅读和已有记录，本次没有重新运行证明检查。

**对总体难度的修正判断**：顶层证明的简化不保证总体证明成本降低。共同规格路线仍需构造规格、证明两侧符合性以及处理表示对应；这些工作可能与直接关系证明一样困难，甚至更多。若规格只是重新编码源程序语义，也未必形成有用的简化。

直接联合验证同样可以组合指令或代码块引理，使用关系不变式，无需同时完全展开两套模型。关系可以具有 `R : State_NEON → State_RVV → Prop` 的形式；两边状态类型不同在逻辑上不构成障碍，但现有工具可能需要适配。这是对证明架构的分析，尚无本项目两条路线的对照实验。

当两份程序结构接近时，直接比较可能利用共同结构，减少分别建立完整功能说明的工作。当共同规格简洁而两侧执行结构差异大时，独立符合性证明可能避免复杂的执行对齐。两条路线都能复用既有证明：共同规格可复用源侧正确性；直接关系证明也可把一个已验证 baseline 的正确性传递给优化版本。具体收益需要测量。已有机器码关系验证工作展示了后一种组合方式，见 [Relational Hoare Logic for Realistically Modelled Machine Code](https://arxiv.org/html/2505.14348v1)。这些案例不等于已有可直接使用的 NEON 到 RVV 工具链，项目适配问题见[直接等价调研](../sail-tooling-gap/DIRECT-EQUIVALENCE.zh-CN.md)。

本项目现有[性能记录](../sail-tooling-gap/kernel-e2e/NOTES-proof-performance.md)指出 RVV load 的 trace、65536 位寄存器表示和证明检查成本等具体困难。更换顶层的组合方式不会自动解决这些底层困难。因此，本想法目前定位为候选的证明组织方式；总成本收益仍是待验证假设。

**下一步候选验证**：在同一个 kernel、同一合法域和观察定义下，对比共同规格路线与直接关系证明路线。尽可能复用相同底层引理，并计入接口或关系逻辑适配成本、人工新增引理和不变式、agent 成本、总检查时间及内存。共同规格路线还需检验顶层能否只组合接口结论。若先使用现有 reduction 的条件性结果，两条路线必须采用相同的 `Hload` 前提，并将其标为尚未闭合的条件性比较。规格的生成方式留待后续讨论。

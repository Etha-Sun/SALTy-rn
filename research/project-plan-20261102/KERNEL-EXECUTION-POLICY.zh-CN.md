# 重要：Kernel 验证执行与多进程协作规范

日期：2026-11-03。状态：**执行要求与设计笔记；本轮仅记录，不实现调度器，不启动 worker 或证明任务。**

适用对象：后续真实 SIMD kernel 的翻译、修复、优化与等价性验证。本文区分用户确定的要求与助手补充建议；未实现的机制不能被汇报为已有能力。

## 1. 用户确定的要求

1. **逐 kernel 记录处理时间和 token 花费**，包括失败、重试、恢复与换模型，不能只统计最后成功的尝试。
2. **建立良好的代码和运行环境，充分利用服务器资源，尽量并行测试与验证。**
3. **充分复用过去已经证明的 kernel、合同、引理和处理经验。**
4. **A → B 时尽量不改 A；对 B 的每项修改都必须有充分理由，影响范围可控、容易审查，尽量保留优化性能。绝不允许通过破坏等价性要求的降级来换取证明通过。**
5. **采用一个监督 agent 管理多个独立 Codex CLI 进程，不使用 subagent 作为 worker。** 监督者跟踪真实工作状态，在中断、无进展或验证器长时间卡住时指导恢复，并直接汇报证明状态。
6. **按经验与难度安排任务。** 有相关经验的 worker 优先继续同类 kernel；困难问题可交给用户指定的更高层级模型，例如 astra。实际可用模型标识、权限与运行配置在实施时核实，不在此宣称已配置。

此前已确认的要求继续适用：`spec / impl / proof` 分离；NEON 个别真实修复可考虑，但逐项确认；不能用许多辅助引理完成的描述代替主目标完成。用户本轮认可版本核对、失败成本、修改独立审查、复用依赖检查、性能隔离和主目标汇报等经验原则；以下具体实现设计仍是建议。

**额度政策更新：用户已撤销此前“quota 至少剩余 50%”的要求。旧交接材料中由此派生的 55% 缓冲停止线及额度未知即停规则也不再适用。** 仍需记录真实成本；这不是对无限预算或新增付费方式的授权。

## 2. 先认清实验对象，再开始花费

每项任务先冻结源码仓库、提交、路径、文件哈希、来源类别（上游发布实现、作者优化版、中间版、项目修复版）以及实际调用契约。目标不只用 kernel 名称标识。

用户最新核查：之前那批 40 个 kernel 属于 Keagan 的中间版本，不能作为最终优化版或 XNNPACK 原版的论文实验；**最终论文实验按尚未建立合格结果处理**。历史证明、工具和经验可以复用，但不能继承错误的源码身份或性能结论。这一口径优先于本目录旧规划中的进度描述。

任务卡至少包含：A/B 身份、目标 ISA/profile、输入域、输出观察、内存条件、证明范围、验收命令、修改权限、预期复用项和预算。目标版本尚未查清时，先做身份核对，不批量启动证明。

## 3. 源码修改的边界

- 原始 A 和原始 B 留存不可变快照；候选改动单独保存，不能覆盖来源。
- 默认保持 A。若怀疑 A 有真实错误，给出触发条件、反例或语义依据，单独提出最小修复，按用户要求逐项确认。证明修复后的 A 与 B 等价，不能代替原 A → B 的结论。
- 对 B 优先调整证明、引理或有对应性依据的前端适配。不能仅因证明困难，把优化 kernel 换成标量参考、删除分支、固定循环长度、丢弃尾部处理或改变舍入/归约行为。
- 不得偷偷缩小合法输入域、排除困难的 NaN/零/溢出案例、放宽输出关系，或引入未解除假设来冒充原目标完成。若原契约有误，提出单独的契约修订与影响说明，保留旧目标的未完成状态。
- 来自真实调用者的参数范围可以成为证明依据，但要提供来源与调用者兑现约束的证据，不能在出现反例后随意加前提。
- 接口适配、运行源码修复、性能优化、规格变化分别记录；宏、helper、生成输入中的语义改动也属于修改，不能藏在主文件 diff 之外。
- 每个补丁只解决一个明确问题；无关清理、全文件格式化与顺手重构不混入。按语义影响评审，不能仅凭修改行数判定安全。

### 反例在原设定中不可行时：允许有依据地加强前置条件

用户明确要求：若 A/B 不对齐且已找到确切反例，应回到原始应用/调用设定检查其可行性。若反例不属于该设定允许的输入，应尝试补充 spec 中遗漏的约束，记录理由，并审核加强的正当性与必要性；不能为了证明容易而排除合法行为。

处理顺序：保存原反例与原 spec → 核实真实调用条件及输入生成关系 → 提出最小必要约束 → 审核约束依据与覆盖范围 → 对双方在修订契约下重新验证。证明与修订获准分别记账。

- “测试未遇到”“通常不会这样调用”“模型觉得不合理”都不是不可行证据。依据应来自公开 API 契约、实际调用者、参数初始化/布局不变量或明确部署设定，并核对两端适用性。
- 若 `R` 表示原设定的所有合法调用状态，`P_new` 是加强后的前置条件，需要证明或提供可审查的充分依据支持 `R ⇒ P_new`；只证明该反例不满足 `P_new` 不够。`R` 本身也必须有独立来源。
- 应核查每条新增约束是否有原设定依据，是否有更弱但同样准确的表达，是否误排除其他合法边界；检查非空性、尾部、参数相关性和别名条件。不能以“必要性”为名要求证明原本未承诺的非法输入。
- 约束若仅由某个应用保证，结论限定于该应用；不能扩称上游 kernel 对所有公开合法输入都正确。若库契约允许反例而当前应用不允许，分别报告库级差异与应用级成立。
- 审计记录包含反例、旧/新 spec diff、不可行性依据、合法域覆盖论证、最小性/必要性说明、审查结论及受影响的重验结果。规格变化不与源码修复混成一个补丁。

这里的“加强 spec”具体指加强前置条件；逻辑上会减少实现的证明义务，因此需要独立审查。若 spec 是对既有合法域的忠实补全，则可以保留原始 kernel，而非制造新的运行时拒绝条件来排除反例。

每项运行源码修改附一条审计记录：

| 必填内容 | 要回答的问题 |
| --- | --- |
| 基线、补丁、修改位置 | 究竟改了哪个版本的哪些行为？ |
| 原因和证据 | 是真实错误、ISA 差异还是前端限制？有什么依据？ |
| 备选方法 | 为什么不能只改证明或适配？为何选择此最小改动？ |
| 契约影响 | 是否改变输入域、数值策略、访存、布局、VL 或前提？ |
| 证明与性能 | 哪些目标已重新验证？前后性能测的是否就是这两个版本？ |
| 审查结论 | 待审、接受或拒绝；接受理由和未解决风险是什么？ |

“修改后的证明通过”和“该修改可接受”分开登记。缺少性能证据时写“未测”，不得宣称无性能影响。用户曾将性能下降至少 20% 定义为严重影响；这不是允许小于 20% 的退化自动通过的门槛。必要的正确性修复如果有明显代价，也必须单列报告，不以错误版本更快为由保留错误。

## 4. 时间、token 与资源台账（建议的记录口径）

以 `kernel_id + candidate_id + attempt_id` 标识一次尝试，绑定 worker、会话 ID、实际模型/推理配置、源码/规格/依赖哈希以及父尝试。换进程或换模型不得清零累计成本。

| 类别 | 记录方式 |
| --- | --- |
| 时间 | 创建、开工、检查开始、检查结束、中断、恢复、完成时间；分开排队、模型处理/工具往返、构建、验证器与人工等待；不能可靠分离的部分明确标未知 |
| Token | 保存原始 usage 事件及字段；分别记输入、缓存输入、输出、推理字段（若接口提供），去重后按尝试与 kernel 汇总 |
| 验证资源 | 每次命令、退出码、墙钟时间、CPU 时间、峰值内存、线程/资源限制、日志位置 |
| 结果 | 成功、反例、超时、内存不足、环境/前端失败、其他未完成；保留所有尝试 |
| 修改与复用 | 修改清单、复用哪些资产及其版本、新增证明、最终候选与性能证据 |

注意：缓存输入通常是输入的子集，推理 token 是否属于输出以实际接口口径为准，不能重复加总。崩溃或缺失事件写“记录不完整”，不能记为零。多个 kernel 混在一次不可分割的会话调用中时，标共享成本，不伪造精确分摊。

公共语义库建设、监督开销和跨 kernel 调试单独记账；报告单 kernel 成本时区分直接成本与共享投入。并行任务的墙钟总工期与各任务累计耗时分别报告。

Token、API 金额和订阅 quota 是不同指标，不能由 token 数臆测 quota 百分比。成本跨所有 worker 与监督进程累计，按实际任务预算与账户限制执行；不设置此前的百分比保留线，也不因额度读数未知自动停止任务。不可观测的数据明确标未知，不能擅自改用付费 API。

## 5. 环境与并行（助手建议，落实用户的资源目标）

- 工具链、验证器、编译器、语义模型、公共合同固定版本；启动先做小型环境检查。环境故障和证明失败分开归因。
- 每个 worker 独立 worktree/候选目录、构建目录和日志目录；一个任务只有一个有效负责人，避免重复计算和并发覆盖。共享依赖按版本只读复用。
- 按 CPU、内存、I/O 和任务实测峰值安排并行度，逐步提高；内存重型证明单独限流。不能把服务器线程数直接当作证明进程数。
- 各 worker 的内部构建线程也计入总预算，避免进程级与构建级并行叠加导致过载。为系统和监督留资源，不影响服务器上的其他工作。
- 性能基准使用隔离或独占资源，避免与重型证明争用；固定编译配置、输入形状、重复测量和测量顺序，保存原始样本与波动。正确性测试可并行，不等于计时实验可无约束并行。
- 运行目录独立编号、日志追加保存、失败可续跑；不能让重跑脚本覆盖历史证据。源码改变后依据依赖关系重验，不全量盲跑，也不能继续使用失效结果。

## 6. 复用历史成果，但核对适用条件

先查相近 kernel、公共 intrinsic 合同、布局引理、循环不变量、尾部处理及失败案例，再开始新证明。按逐元素、归约、量化、重排、GEMM 等类别整理可复用资产。

复用前核对源代码、契约、模型、工具链、ISA/profile 和依赖版本；存在差异时明确需要补的对应证明。历史 `.vo`、`Qed` 或成功日志不是新候选已验证的证据。

公共库新增内容经检查后再供其他 worker 使用；共享模型或合同变动必须标出受影响任务并重新验收。抽取复用项不得削弱公共规格。相似 kernel 可复用证明方法，不因名字相似继承结论。

## 7. 独立 Codex CLI worker 的监督方案

这是用户指定的组织方式，以下为尚未实现的职责设计：

```text
用户：确定目标、修改边界和预算
  └─ 监督 agent：分配、检查证据、诊断阻塞、交接、汇报
       ├─ 独立 Codex CLI worker：逐元素/位操作
       ├─ 独立 Codex CLI worker：量化/布局
       └─ 独立 Codex CLI worker：困难证明或公共阻塞
```

分类是示意，按实际任务和资源调整。worker 不是内置 subagent；监督者不必另有更高权限，也不得绕过用户修改边界。

### 分工与模型升级

- 优先让熟悉同类合同和模型的 worker 继续相近任务；经验同时落入文件，不能只依赖长会话记忆。
- 常规任务可沿用用户此前偏好的 sol6.1；出现新的语义难题、困难不变量或多个任务共享的阻塞时，再考虑交给 astra 等用户指定模型。此处是分配偏好，不是模型性能或可用性保证。
- 升级前区分推理难题与工具/资源故障；OOM、缺依赖或前端缺陷不能靠一味换大模型解决。
- 交接包含精确目标、当前补丁、已复用资产、失败命令、最小反例/卡点、预算和下一步假设；避免新 worker 从头重读整个仓库。

### 监督与恢复

- 同时检查进程/子进程、CPU/内存、日志事件、检查器状态及产物变化；“进程存在”不是有进展，“暂时无输出”也不是卡死。
- 长证明设置事先明确、可调整的时间和内存预算。预算内健康计算允许继续；异常时先诊断，再决定续跑、缩小诊断任务、补引理或升级处理。缩小诊断任务不改变最终证明域。
- 中断后检查是否仍有验证器子进程，恢复到明确的候选和会话；避免同一证明重复启动。进程退出码为零只说明进程正常结束，不代表任务完成。
- 同一失败在输入、方法和环境均无变化时，不无限重试。监督者要求新的诊断假设或明确记录阻塞，不能靠不断提醒“继续”制造活动。
- 监督者应提供具体指引，例如复用某合同、检查某前提、制作前端最小复现；不得指示 worker 降低规格换通过。
- 建议使用轻量进程服务保存任务与事件，仅在需要判断时唤起监督模型；避免高频 LLM 轮询消耗预算。监督进程本身也需可恢复；没有运行宿主和恢复机制时，不能承诺聊天结束后持续监督。

官方文档提供了非交互 `codex exec --json` 的事件/usage 输出与按明确会话 ID 恢复的接口，可作为后续实现依据。实施前核对服务器安装版本；多 worker 不依赖含糊的 `--last`。这些接口本身并不等于已有调度、存活检查或运行中指导能力，具体指导通道需在实现时验证。[OpenAI：Non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)

## 8. 验收与汇报：围绕主目标

助手补充的经验建议：

1. **保持 spec / impl / proof 分离。** 普通函数体必须有对应证明；仅把两个未验证函数声明为满足相同合同，再证明比较器返回真，不能算 kernel 等价性完成。
2. **检查证明是否真的覆盖目标。** 记录未解除前提、信任假设、合法域是否非空、固定 VLEN 等边界；部分正确性不自动包含终止性或真实 ISA/编译器端到端正确性。
3. **整体验收绑定最终文件。** 在固定依赖环境检查主定理及完整依赖，核对源文件哈希；用有区分力的测试/已知反例辅助检查模型与接口，但不把测试当证明。
4. **明确输出观察的组合边界。** 忽略 NaN payload、合并正负零不代表任意调用者都可安全替换；程序级使用需证明实际调用者尊重该关系，或加强中间合同。
5. **证明状态与性能状态分开。** 尚未证明、明确不等价、环境阻塞、已验证但性能未测都单独呈现。证明困难时可以报告没有完成，不得伪装成功。
6. **保留反例和失败经验。** 分开记录实现错误、规格差异、模型/前端问题和资源问题，供下一项复用；不能只保留成功故事。

每项汇报使用以下简表，详细诊断另附链接：

| Kernel / 精确版本 | 主目标是否完成 | A/B 修改与理由 | 累计时间 / token | 性能状态 | 卡点与下一步 |
| --- | --- | --- | --- | --- | --- |
| 待填 | 已验证 / 未完成 / 已有反例 | 原样或可审补丁 | 含失败与重试，未知显式标注 | 已测 / 未测 / 回退 | 具体问题，不列无关阶段 |

监督者汇报真实状态变化、关键阻塞、预算风险和完成结果；更新频率在启动时约定。用户问进度时，直接回答目标还差什么，不用辅助引理数量替代完成度。

## 9. 后续实施顺序（建议，当前不执行）

先用一个简单 kernel 验证目录隔离、成本记录、主目标验收和中断恢复；再用两个同类 kernel 检查复用与分配；然后逐步增加并行度和模型分工。先确认监督能发现“退出但没完成”“验证器仍在运行”“源码已变化”等情况，再启动批量任务。

本文只保存要求与建议，没有启动新 Codex 进程、配置后台服务、修改 kernel、运行证明或重测性能。

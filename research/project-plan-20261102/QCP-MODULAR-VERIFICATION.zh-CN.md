# QCP 在证明什么，以及优化候选能否增量验证

2026-11-02。源码阅读、历史日志统计及一手文献调研；没有重跑长证明，没有测得新的加速比，没有修改 kernel、规格或既有准入规则。

## 用户问题与结论

用户已经做过优化/验证实验并确认验证很慢。本次不把“首次测证明成本”作为下一步，也不要求 agent 只能使用固定优化菜单。研究两点：任意提出修改，但模块化的修改可以走快速验证路径；使用已证明 pre/post 契约复用其内部证明。

结论：两个直觉都成立，但后者已经是 QCP 和当前项目的基本机制。新增工作在于让逻辑上的模块化真正转化为跨候选的计算复用，并处理函数内修改。小源码 diff 不保证小证明 diff。可提出的研究假设是“稳定接口以内的修改只承担受影响区域及组合的验证成本”；当前没有可宣称的量化收益。

## 2. 项目目录与证明链

以 `verified/f32-vadd/` 为具体例子：

| 文件/目录 | 作用 |
|---|---|
| `impl/testNEON.c`, `impl/testRVV.c` | 实际要验证的 C；本例逐字保留原件 |
| `spec.c` | 两侧 kernel 的 Require/Ensure；比较器与 equivalent 的实际 C 及合同 |
| `contracts/` 与共享 shim | 数学模型、内存谓词、intrinsic 解释及前端绑定 |
| `proof/annotations/`, `proof/c/` | 循环不变量、Assert、策略，不是另一份运行实现 |
| `proof/prepare.py` | 把当前 impl 与 spec、证明注释组合成验证输入 |
| `.build/<run>/units/` | 本轮实际注释 C、CPP 后 C、QCP 输出 |
| `proof/coq/*_goal.v` | 生成的 VC 命题和 `VC_Correct` 接口 |
| `*_checked.v`、各 Leaf/Facts/Tactics 文件 | 满足 VC 的证明，以及可复用数学引理/证明方法 |
| `proof/check.py`, `coverage.py`, 最终 gate | 核对来源、调用合同/函数体闭包，强制完成所有 `VC_Correct` 字段 |
| manifest/status/evidence | 绑定输入、命令、依赖、结果；不是证明本身 |

QCP 的通常输出名称为 goal、auto、manual、check；本项目将完成证明整理为 checked/Leaf 等模块，不能通过命名判断是否已经验证。

实际链条为：

```text
公开 spec + 原始 impl + 注释 + intrinsic 语义
                ↓ 预处理、源码绑定、QCP 符号执行
两侧 kernel / helper / caller 各自的 VC
                ↓ 自动证明、补充 Coq 引理与策略
每个实际 C 单元的 VC_Correct
                ↓ 调用闭包、合同一致性、最终门禁
既定 C-shim/输入域/观察关系下的模块化部分正确性
```

不是先得到一个只关于数值的 equivalence 大定理、再把一切义务从它机械分割出来。各函数按自己的契约生成 VC；数学结果关系也有独立引理；顶层 caller 使用两侧已经建立的合同。

## 3. equivalent 的具体含义

VADD `spec.c` 中两端合同都规定输出为 `vadd_values(n,A,B)`，并返还输入资源。`equivalent` 顺序调用两端，再调用 `compare_outputs`；最终 Ensure 显式要求 `outputs_related(L,R)` 和返回 1。

关键事实：`compare_outputs` 的 Require **已经要求** `outputs_related(L,R)`。其证明说明已相关输出会返回 1，不是在此重新证明任意两个黑盒程序等价。实际输出相关性来自两侧函数体满足结果模型的证据。缺失任一 body 证明，仅编译 wrapper 是条件式结论。

`VaddWrapper/wrapper_goal.v` 有安全性、调用前提、返回与 partial_solve 等义务。`wrapper_checked.v` 的返回证明为左右输出都选择 `vadd_values n A B`，再应用 `identical_outputs_are_related`。这解释了顶层组合为什么可以很短。

本例 wrapper 有 9 个实际字段；不能把它们的通过当成全核通过。`coverage.py` 中 `Module Check_... : ...VC_Correct := ...` 检查接口完整性，同时 Python 检查普通 C 调用闭包和合同对应。不是单看文件里有没有 Qed。

`review-only` 明确以两侧 kernel 合同为假设；其历史 37 秒不能当作完整 VADD 从约 380 秒加速到 37 秒。

## 4. 多种 VC 究竟要求什么

| 名称/来源 | 典型义务 | 为什么等价性需要它 |
|---|---|---|
| safety | 长度/算术范围、合法表达式条件 | 值相等不能掩盖未定义行为 |
| entail / call | 当前资源满足被调函数 Require，计算剩余 frame | 不能无条件借用 callee 的 Ensure |
| 循环入口 | 初始状态蕴含不变量 | 建立“已处理前缀正确”等关系 |
| 循环保持 | 任意一次合法迭代之后仍满足不变量 | 用有限义务覆盖任意合法迭代次数 |
| return | 不变量加退出条件蕴含 Ensure | 把局部推理连接到完整输出 |
| partial_solve / pure / aux | 断言变换剩余部分、纯事实与空间资源 | 标签本身不说明容易或不重要 |
| strategy | 自定义断言变换策略的正确性 | 自动整理内存资源必须有依据 |

你要补的通常是 Coq 证明或证明注释，不是改可执行 C 来凑证明。QCP 也不会简单运行循环 n 次；循环不变量是关键。仍需区分“若返回则满足结果”的部分正确性与终止性。

## 6. 为什么已有契约仍然慢

**逻辑模块化、证明脚本复用、编译结果复用是三件不同的事。** 同一个 tactic 能重用，不代表重跑它很快；所有叶子分别有证明，不代表编译依赖足够细。

VADD `check.py` 默认建立全新 run，重新生成所有单位 VC，再 fresh 编译本地模块。`--resume-run` 只允许同一次中断任务恢复，核对 spec、源、CPP、Coq 内容及参数未变；不是接受修改后候选的增量模式。Exp `check_full.py` 同样建立新目录，并明确 `no_component_vo_reused=True`。这是严格重放策略，本身不是逻辑上每次必须重做一切。

因此，直接比较“全冷启动封存检查”与“新缓存热启动”，不能充当新的验证算法贡献。首先应把可靠的常规依赖缓存作为强基线，另列最终完整审计成本。

## 7. 第二个直觉：pre/post 复用有效，但需要完整接口

已有 `{P} B {Q}`。替换为 B' 时，只要重新证明 `{P} B' {Q}`，原调用方在依赖相同接口且语义未变时可复用。若改变合同，至少需证明旧调用状态满足新前提，且新后置足以推出调用方需要的旧后置；效果/所有权变化也必须纳入。

对 SIMD 区块，P/Q 应描述所处理的逻辑元素、索引对应、可读写区间、live-out 值、未写区域 frame、别名/对齐、VL/capacity/mask/tail 约束。只写“返回值相等”不够约束越界写、额外读取、隐含状态或后续使用的中间值。

参数化区块合同可以写成：给定可访问输入/输出切片和 `0 < k <= capacity`，执行后前 k 个元素满足既定逐元素函数、输入不变、切片外输出不变。向量类型/分组的表示关系放到内部，避免合同把 LMUL 常量或某种展开方式写死。

也不能只证明“两个实现均满足同一个任意弱 spec”就声称等价。例如只规定输出非负，输出 1 与输出 2 都满足却不等价。共同结果模型必须把观察唯一确定到所需等价类，或另外证明关系。NaN payload/±0 的宽松关系可以用于最终输出；不能自动用于所有内部边界，后续 copysign/位观察可能区分它们。

注意：**证明中的区块无需强制成为真实 C helper 调用。** 可以保留原始内联 kernel，通过逻辑切点和区块定理分隔；但仅插 Assert 不会自动得到可缓存的独立 C 区块证明，还需要实际代码与区块定理的绑定、控制流与 frame 组合检查。当前框架尚未提供通用机制。不能再用拆 runtime helper 的方式把证明复用换成性能损失。

## 8. 第一个直觉：开放修改空间，局部修改获得快速路径

以下三层可以逐步落实，均保持失败时退回较大范围验证：

1. **依赖级复用**：未变 NEON、共享库、模型和普通 helper 的已检查产物，绑定源码、合同、语义定义、工具/参数、递归依赖和已验证状态。新最终证书仍需闭合全部依赖，不能凭某个 status 的 passed 或 .vo 存在跳过。
2. **义务级复用**：本轮生成真实 VC，识别未变命题及其完整逻辑环境，复用对应已检查证明；改变的 VC 尝试旧脚本，失败再补证。需要解决单一大 goal 模块的依赖扩散、自动变量/编号漂移。相似文本仅是匹配提示，不能视为证明。
3. **语义区块复用**：旧/新区块可能拥有不同内部 VC，只要两者符合稳定接口即可复用外层证明。可用参数化切片/循环分块定理支撑配置修改，或用旧新区块的关系证明建立接口保持。

配置变化不天然局部：LMUL 会改变容量、类型、实际 VL、tail 与资源模型；展开可能改变循环边界，浮点归约重结合会改变结果。参数化定理需要先证明，不能把已证常量4直接替换为8。

“不限制 agent”可以指不限定编辑菜单、不限定必须保留某种模块结构；它不等于支持任意 C 语法或每种改动都可快速证明。跨边界改写应扩大验证范围；范围扩到整核也能提交，只是可能慢或 unknown，不能为命中缓存缩小输入域。

## 9. 文献位置与可以诚实声称什么

- [QCP 论文](https://arxiv.org/html/2505.12878v1) §1、§4：函数调用按合同处理，符号执行产生 VC，自动处理与 Rocq 补证结合；§6.1 明确其当时符号执行器缺乏形式健全性证明。本项目最终 gate 不能消除 QCP 前端/VC 生成和 C-shim→真实 intrinsic 的信任边界。本次没有核实更新版本已经补齐该元定理。
- [QCP 官方教程](https://www.qua.codes/en/tutorials/index.html) T1/T3：Require/Ensure、循环不变量及断言蕴含；支持上述解释。
- [Leino–Wüstholz, CAV 2015](https://pm.inf.ethz.ch/publications/LeinoWuestholz2015.pdf)：利用调用图、控制流图做细粒度验证结果复用。故“程序小改只重验一部分”不是新的总概念。
- [Why3 controller 文档](https://why3.org/api/Controller_itp.html)：旧证明尝试匹配到新目标时，目标变更要标 obsolete；证明脚本重用不等于旧结果仍成立。
- [Coq 8.20.1 官方手册](https://rocq-prover.org/doc/V8.20.1/refman/practical-tools/coq-commands.html)：coqc 编译脚本、coqchk 检查编译库；仅导入既有产物与 fresh 重跑脚本的成本不同，缓存需要来源与环境绑定。跳过 opaque proof 的开发接口模式不能作为最终完成证据。
- [Differential Assertion Checking, FSE 2013](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/paper-34.pdf)：使用旧新版本关系及模块化推理。其“不新增断言失败”本身不等于完整输出等价，只能借鉴关系分解方法，不能降低本项目目标。

可作为候选论文问题：**能否让自由生成的 SIMD 优化保持可复用的验证接口，在不改写运行实现、不放宽公开契约的条件下，使验证成本随受影响语义区域而非整个 kernel 增长？** 这不是已实现或已有加速证据。

## 10. 下一步应补什么，而不是重做已有实验

先从现有候选及历史证明选择真实差异，重放时增加计时归因；没有完整可复现时间戳的历史记录不补造墙钟。

对照应包含：当前 fresh gate、常规函数/模块依赖缓存、VC 级复用、稳定区块接口；逐渐增加机制，分清工程重编译收益与证明推理收益。

修改族包括：不变源重放（缓存成本对照）、接口内小改、LMUL/展开参数改、尾部改、跨区块循环调整。至少一个预期失去复用的有效大改和一个语义错误负例。不能只选缓存容易命中的版本。

记录：端到端墙钟及关键路径、QCP生成、导入/脚本执行/证明检查、目标数与内容未变数、实际复用数、接口失效传播、证明修补与失败次数、峰值内存、最终性能。结果必须与同一源码/profile的 fresh gate 一致；测试还应修改被调函数/语义定义而保留顶层名字，确认缓存失效，防止复用过期证明。

优先诊断 Exp 中现成的长 frame 义务及 VADD 的未变依赖，避免首先再建设四端通用优化系统。后台 vabs 保持原任务，当前结果仅作为共享组件接口试点。

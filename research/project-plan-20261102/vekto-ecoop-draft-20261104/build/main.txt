Introduction
5
Efficient numerical software depends on kernels that exploit the execution and memory
6
organization of the target processor. Developing these kernels requires choices about data
7
layout, vectorization, blocking, and instruction scheduling that are difficult to make uniformly
8
across hardware platforms. Recent work investigates language-model agents as a means
9
of exploring this implementation space. KernelBench evaluates generated GPU kernels
10
against reference tensor computations, while Autocomp combines hardware knowledge with
11
correctness and performance feedback to search for faster accelerator programs [12, 7]. These
12
systems demonstrate opportunities for automating kernel development, while making the
13
reliability of generated implementations an increasingly practical concern.
14
We focus on SIMD and vector kernels written using C intrinsics. Vector extensions
15
in modern CPUs expose different execution models: Arm NEON operates on fixed-width
16
vectors, whereas RISC-V Vector (RVV) provides runtime selection of the number of active
17
elements [2, 15]. These differences affect loop structure, tail processing, and memory accesses.
18
Architectures also differ in their numerical operations, even when the operations have similar
19
names. RVV has attracted dedicated work on porting existing intrinsic code, including
20
SALTyRN and IntrinTrans [5, 6]. Compiler intrinsic interfaces make such work possible within
21
C: programmers combine ordinary control flow and pointer manipulation with architecture-
22
specific operations that the compiler lowers to target instructions. Intrinsics expose hardware
23
capabilities without requiring an entire kernel to be written in assembly, but do not make its
24
behavior portable by construction.
25
This interface also gives agents a concrete programming environment in which to apply
26
instruction descriptions and optimization guidance. SALTyRN translates NEON kernels
27
to RVV and applies an Autocomp-based optimization stage [5]. Correctness remains a
28
separate obligation. KernelBench’s maintainers document generated programs that exploit
29
evaluation weaknesses, including output-memory reuse and misleading timing [8]. Existing
30
systems address correctness in several ways: Autocomp tests candidates against reference
31
implementations, IntrinTrans uses compile-and-test feedback, SALTyRN performs bounded
32
symbolic equivalence checking, and LLM-Vectorizer uses Alive2 to validate vectorization [7,
33
6, 5, 17]. Our question is how to establish a whole-kernel guarantee for the stated input
34
domain, including loop iterations and memory accesses, while retaining the implementation
35
produced by optimization. Such a guarantee can reject functional deviations that escape
36
tests; it does not by itself prevent timing manipulation or other attacks on a benchmark
37
harness.
38
The semantic interface for this verification can be placed at several levels.
At the
39
machine-code level, Sail supplies detailed ISA definitions, and Islaris supports program
40
proofs against authoritative instruction semantics [3, 16]. At the intermediate-representation
41
level, Alive2 checks LLVM transformations, while Rake synthesizes semantically equivalent
42
vector instruction sequences for Hexagon HVX from Halide expressions [10, 1]. An IR-based
43
comparison must account for the lowering of intrinsics and the memory semantics of the
44
selected IR. C intrinsics offer another boundary: an executable C interpretation of each
45
supported intrinsic can expose its behavior to a C program verifier, allowing the surrounding
46
loops and pointer operations to remain in the language in which the kernel was written.

2
Verifying Semantic Equivalence of SIMD Kernels Across Architectures
We choose this C-level boundary to study functional equivalence under explicit calling
48
contracts.
The observations are the specified outputs and memory effects of ordinary
49
kernel calls, under a stated floating-point and vector configuration. Interrupt handling,
50
privileged execution, and timing are outside this observation.
NaNs, infinities, integer
51
overflow conditions, and invalid memory accesses still require treatment whenever they
52
affect an admitted call. A binary-level proof can support a stronger connection to machine
53
execution, but also requires relating machine states and establishing the relevant execution
54
environment. Our C-level design keeps the proof interface close to the intrinsic source and
55
permits reuse of C verification infrastructure. It introduces its own obligations: the intrinsic
56
interpretations and the preparation of verification inputs must faithfully represent the source.
57
We therefore retain these correspondences as explicit trust boundaries.
58
We present Vekto, a framework for checking semantic equivalence between intrinsic
59
kernels through reusable C semantic shims and modular proofs. The design covers Arm
60
NEON, RVV, x86 AVX, and Hexagon HVX through a common contract interface. [TODO:
61

62
ISA; four complete backends are not yet an experimental result.] For each kernel pair,
63
Vekto associates intrinsic calls with their semantic definitions and expresses the required
64
output relation in a public specification. It separates the implementation, specification, and
65
proof annotations so that proof development need not rewrite the executable algorithm.
66
QCP symbolically executes the annotated C programs and generates verification conditions,
67
which are discharged through its automation and Rocq/Coq proofs [18]. The implementation
68
proofs establish the contracts used in the final equivalence argument. An unresolved proof
69
obligation remains unresolved unless a checked proof or a reproducible counterexample is
70
obtained.
71
The workflow concentrates per-kernel review on the calling contract, verification evidence,
72
and any proposed implementation changes. A compact public specification provides an entry
73
point to this review; its imported mathematical definitions and memory predicates remain
74
part of what must be justified. When a counterexample violates a documented assumption
75
of the original caller, the specification may be strengthened to express that assumption,
76
provided the revised domain still includes all legitimate calls. When the counterexample
77
is feasible, the target implementation requires repair or the claimed equivalence must be
78
rejected. Repairs are reviewed as executable changes and measured for their performance
79
effect before the revised candidate is accepted. Shared semantic models and the verification
80
toolchain require separate review, so this workflow does not presume that reading a short
81
specification is sufficient to establish trust in the entire system.
82
The same equivalence interface serves three uses. First, it validates optimizations within
83
an ISA or translations across ISAs against a reference implementation, without making the
84
optimizer itself part of the trusted reasoning. Second, it supports porting kernels from existing
85
NEON or AVX implementations to target libraries whose coverage of the selected operations
86
is incomplete. Here RVV and Hexagon HVX are target backends; the motivation is missing
87
implementations in a particular library, rather than a claim that both architectures are new.
88
Third, it supports semantic cross-checking of independently developed implementations of
89
the same operation. Differential testing compares executions on selected inputs [11]; program
90
equivalence checking, exemplified by SymDiff [9], makes the relationship itself the verification
91
target. A concrete disagreement can then be classified as an implementation defect, an
92
allowed numerical difference, an unsupported calling assumption, or a modeling error. This
93
classification identifies whether maintenance requires a code repair, a clearer contract, or a
94
correction to the verification model.

Consider an elementwise maximum kernel that reads two binary32 arrays and writes
112

113

114

115

116

117
arguments about the processed prefix and valid memory accesses. In particular, the NEON
118
tail requires readable padding even when only one output element is requested.
119
The numerical operations also differ. For the Arm floating-point profile used in this
120
example, vmaxq_f32 propagates a NaN operand. RVV’s vfmax returns the numerical operand
121

122
maximum would erase the difference before any program proof began. The semantic shims
123
instead retain separate lane functions. Figure 2 extracts these functions from the existing
124
QCP shim: the Arm branch quiets signaling NaNs and preserves a NaN result, whereas
125

3.1
The relation being checked
168
Let x be a logical input, including array contents, dimensions, and operation parameters. A
169
domain predicate D(x) describes legitimate calls. For implementation Ki, a precondition
170
Pi(x, si) relates x to the initial C state si, including its memory representation. A machine
171
profile pi records the ABI, relevant floating-point configuration, and supported vector
172
configuration. The two profiles need not use the same vector width or state representation.
173
For integer results we require exact equality. For the floating-point outputs considered
174
here, define

3.2
Relating implementations through a common specification
191
Each implementation is checked against a postcondition that relates its output to a common
192
relation S(x, o). To compose the results into equivalence, the common relation must determine
193
observations up to the selected equivalence:
194
S(x, o1) ∧S(x, o2) =⇒o1 ≈o2.
(3)
195
This condition prevents a weak common specification, such as a broad error interval, from
196
being mistaken for an equivalence proof. For a reference-preserving floating-point optimization,
197
S may encode the reference’s rounding and accumulation order rather than ideal real
198
arithmetic. The proof must establish the result for each complete implementation, including
199
helpers and tails. A wrapper that assumes both kernel contracts only establishes the final
200
composition conditional on those contracts.
201
The relation in Equation 1 is a final-output observation. It cannot be substituted for
202
bit-level equality at every intermediate boundary: a subsequent reciprocal or sign-sensitive
203
operation can distinguish positive from negative zero. A composed program therefore needs
204
intermediate contracts strong enough for each consumer, or a proof that the consumer
205
respects the chosen relation.

3.3
What QCP checks
207
QCP processes contracts, assertions, and loop invariants by symbolic execution in separation
208
logic [18, 13]. In the inspected VADD package, the public contract supplies readable input
209
arrays, additional padding for NEON tail loads, and a separate writable output array. It
210
returns the original input resources and a fully initialized output array with specified values.
211
At an indexed read, generated entailments expose the cell at the requested index from the
212
array predicate and retain the remainder of the array. Other conditions establish expression
213
ranges, satisfy callee preconditions, preserve loop invariants, and derive the postcondition on
214
return. Memory-access validity is checked through these resources and entailments as well as
215
symbolic-execution failures; it is not confined to obligations named safety [14].
216
The proof package checks generated VC_Correct interfaces for the kernel bodies, shims,
217
helpers, and final comparator. Statements declared inside such an interface are obliga-
218
tions to implement, not evidence that the obligations have been proved. The implementa-
219
tion/specification binding and dependency checks are therefore part of accepting a result.
220
The inspected package establishes modeled C-shim partial correctness and explicitly excludes
221
hardware-to-shim correspondence and termination. [TODO: Freeze the release and complete
222
the per-kernel coverage audit for the final experimental cohort.]

3.4
Review and trust boundaries
224
Reusing a semantic shim requires a matching operation, type, and machine profile. In
225
particular, a proof at one fixed RVV capacity is not a proof for all hardware VLENs. A
226
sound generalization must account for the allowed active-length choices and the behavior of
227
inactive or masked lanes. Source preparation must also preserve executable statements and
228
their interpretation. Compiler correctness and the correspondence from modeled intrinsic
229
semantics to native execution remain outside the present proof chain. The QCP paper reports
230
that its symbolic executor lacked a formal soundness proof at publication [18]; [TODO: audit
231
the exact QCP release used in the final artifact and state its remaining trusted components.]
232
When strengthening a precondition from P to P ′, let R describe the original caller’s
233
legitimate states. Acceptance requires evidence for R ⇒P ′, not merely that P ′ excludes
234
one counterexample. Likewise, changing a target creates a new candidate whose proof and
235
timing evidence must be rebound to the changed source. Source edits, contract changes, and
236
proof-only changes are recorded separately. A failed proof, a replayed counterexample, and a
237
completed proof are distinct outcomes.

Generation and validation of optimized kernels.
272
KernelBench, Autocomp, and IntrinTrans use executable feedback to evaluate or improve
273
generated kernels [12, 7, 6]. SALTyRN also includes bounded symbolic comparison before
274
and after optimization [5]. LLM-Vectorizer combines generation with Alive2 validation and
275
describes loop-alignment techniques and restrictions for its experiments [17]. These systems
276
motivate comparing the input domain, semantic model, and complete program obligations
277
of each guarantee, rather than grouping all prior validation as testing. Vekto’s proposed
278
evaluation asks whether modular C proofs can cover the actual optimized kernels under
279
explicit contracts.
280
Semantic models and verified transformations.
281
Sail and Islaris provide a path from authoritative ISA specifications to machine-code rea-
282
soning [3, 16]. Alive2 checks LLVM refinement with bounded reasoning about loops [10].
283
Rake checks equivalence of synthesized vector instruction sequences for Hexagon HVX [1].
284
These operate at different boundaries from Vekto’s C intrinsic interface. The proposed
285
method uses QCP’s existing C verification infrastructure [18]; reusable cross-ISA semantic
286
definitions, the alignment of kernel contracts, and evidence about optimized implementations
287
must supply the contribution beyond that infrastructure.
288
Cross-checking implementations.
289
Differential testing uses disagreements among implementations to identify candidate de-
290
fects [11]. SymDiff checks equivalence and exposes behavioral differences between imperative
291
programs [9]. Our proposed XNNPACK study applies an explicit observation relation to
292
corresponding ISA implementations, while retaining the distinction between disagreement
293
and violation of a required contract. The distinction has practical consequences: a historical
294
XNNPACK min/max policy permits unspecified NaN behavior [19], while a later change to
295
the repository’s separate YNNPACK subsystem adds NaN propagation for a reported JAX
296
reduction problem [21]. That change is evidence of an integration concern, not proof that
297
our tested XNNPACK microkernels violate their API.

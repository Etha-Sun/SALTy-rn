## 我们想做什么

**对真实 SIMD intrinsic C kernel 的跨 ISA 迁移与同 ISA 优化，复用一套明确的语义合同和验证基础，同时测量正确性、性能及验证成本。**

- **Translation**：利用已有 NEON 等实现，生成或接入 RVV、AVX、Hexagon/HVX 实现。
- **Optimization**：改变向量分块、循环、访存和指令组合，提高目标平台性能。
- **Verification**：在冻结的输入域、内存条件、数值观察和硬件配置下，检查具体实现版本的行为。

候选代码可以来自 LLM、人工或现成库。生成器提出候选，目标平台判断性能，证明器检查声明的保证；三者的成功分别记账。

## 为什么值得做

SALTyRN 的动机是复用成熟 NEON 代码、服务 RVV 软件生态，同时避免固定宽度的机械移植浪费目标性能。它已经包含迁移、有界符号验证、优化及最终再验证。Autocomp 则提供硬件反馈驱动的候选搜索。我们的研究问题应放在**真实 C 循环和内存的模块化验证、源码修改的代价、模型审查与证明复用**上。[SALTyRN 作者报告](https://riseproject.dev/2026/07/27/saltyrn-turning-neon-kernels-into-fast-verified-rvv-code-with-llms/)、[Autocomp v3](https://arxiv.org/html/2505.18574v3)

ECOOP Experience 允许研究既有 PL 技术在实践中的应用及负结果。系统结构简单并不妨碍写作，但需要能复查、能推广的经验；“用了 C shim”或“多了几个后端”本身不足以承担论文贡献。[ECOOP 类别说明](https://2027.ecoop.org/track/ecoop-2027-technical-papers)

## 框架怎样形式化

把每个节点定义为 **具体 C 版本＋ISA/profile＋intrinsic 语义环境＋合法输入域＋输出/内存观察**。intrinsic 可以由公开合同与 Coq 定义描述，不要求全部另写 C body；普通 helper 仍须验证实际函数体。

给程序建立 Hoare 合同，证明循环、调用前提、内存与返回结果。两侧可分别符合共同规格，也可直接证明结果关系。必须明确位模式相等、数值相等或双方 NaN 等不同观察；部分正确性不自动包含终止性。跨 ISA 边与同 ISA 优化边使用同样的身份和合同规则。

论文真正需要补强的是原 C→适配输入的对应、intrinsic 模型审核及组合条件，不是增加符号数量。[完整形式化草案](README.zh-CN.md#4-如何用-pl-论文的方式形式化)列出了判断式、关系定义和信任边界。

## 扩展选哪些 kernel

之前的固定 XNNPACK 快照有 **77 个四端源码交集条目**；它们不是77组已知等价程序。[精选32个源码入口](XNNPACK-SAMPLES.zh-CN.md)

| 优先级 | 样本 | 代表能力 |
|---|---|---|
| 第一批 | `s8-vclamp`、`f32-vabs`、`f32-vcopysign` | 精确整数/位操作、不同宽度与tail |
| 第三ISA试点 | `f32-vadd` 的 AVX 实现 | 接现有浮点经验，处理AVX mask与地址操作 |
| 第二批 | `qs8-vadd`、`qs8-rdsum`、`x32-transposec` | 量化、归约、二维布局与复杂访存 |
| 观察敏感性样本 | `f32-vneg` | 零符号差异仅反驳逐位等价；在用户采用的数值相等或双方NaN规则下不构成反例 |

HVX 先从整数/位操作切入；浮点版本、近似除法、归约顺序和大范围tail读取必须先查清。四端现成实现的验证不等于已经实现四向自动翻译。

## 论文需要哪些实验

1. **全40项覆盖与审计**：原版/修复版、批准状态、证明范围、反例、失败和重验情况。
2. **错误与验证能力**：同一合法域下，随机测试、有界检查和完整 C 证明分别发现什么。
3. **修改代价**：源码与helper改动、前端适配成本、修复是否牺牲性能。
4. **全40项性能台账＋代表优化闭环**：已验收baseline、仅测试赢家、形式验收赢家，在相同目标平台与profile下比较。
5. **复用成本**：新增ISA/新kernel需要多少模型、证明、时间和人工审查；基线也允许复用参考证明。
6. **边界分析**：tail、VL、NaN/±0、alias、padding与工具资源；负结果单列。

LOC 分开统计原始C、实际C、helper、intrinsic合同/语义、手写证明、生成证明和工具代码，并同时报告重复与共享。行数不是核心效果指标，需配合时间、内存、审核量和语义范围。

## 后续顺序

**先收束现有证据 → 做迁移/优化/验证的小闭环 → 完成全kernel性能台账 → 接AVX及精选HVX → 收束论文。**

以已核对的固定提交为基线，逐项明确源码修复接受状态；挑3个不同类型的kernel把源码、证明和性能配置绑定。之前聊天提到的Maxpool/HWC版本可能在其他分支或服务器，作为后续核对项，不阻塞规划和其他样本。当前已有性能候选多在VLEN512测量，而许多证明固定VLEN128，这个缺口必须补齐。

论文可按“动机与例子→合同和保证→系统→六组实验→经验与限制→相关工作”组织。主张暂定为可审查整核验证、支持有价值的优化、降低增量验证成本；后两项尚待实验支持。四端全覆盖和已验证优化规则库保留为可选扩展，不作为未完成却必须宣称的成果。
